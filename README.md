# 视频整理与4K成片工程分享包

这是一个可复用的视频工程模板，记录了本项目中“分集视频排序、旁白生成、字幕制作、画面时长适配、4K导出和交付核验”的完整经验。解压后先读本文，再读 `docs/视频制作经验规则.md`。

包内不包含视频、音频、模型、模型缓存、Python虚拟环境、最终成片和大体积中间文件。这样便于分享，也避免把用户素材和个人声音带给其他人。使用者需要把自己的素材放入约定目录，并自行准备运行环境。

## 一、目录约定

在工程根目录建立以下结构：

```text
项目根目录/
├─ README.md
├─ docs/
├─ scripts/
├─ templates/
├─ project_config.json       # 当前本地项目配置，可按需修改
├─ mp4/
│  ├─ 第1集/                 # 先按这个数字排序
│  │  ├─ shot0010.mp4        # 再按集内shot数字排序
│  │  └─ shot0020.mp4
│  └─ 第2集/
├─ wav/
│  ├─ 参考配音.wav
│  └─ 其他配音.wav
├─ 剧本.md
├─ work/
└─ output/
```

`mp4/` 和 `wav/` 是输入目录，不要把它们打包分享。集数必须从外层文件夹读取，不能把所有文件按全局 shot 编号混在一起，也不能用文件名里的 `sc` 编号替代集数。第2集只有一个素材时，就只使用现存的一个。

本工程已附带 `project_config.json`，默认配置对应当前本地目录结构。若把工程移动到其他位置，只需修改其中的相对目录或文件名；脚本会相对于工程根目录解析，不依赖原作者电脑路径。

## 二、推荐操作流程

### 1. 清点素材

把视频、配音和剧本放好后运行：

```powershell
python scripts/scan_assets.py
```

脚本会生成 `work/asset_inventory.json`，记录每个视频的集数、shot、时长、分辨率、帧率、是否带原声和 SHA-256。先检查这份清单，确认排序和素材数量正确，再进入剪辑。

同时抽取每个视频的开头、中间、结尾画面，确认画面内容、静止尾段、原生字幕和可能的错字。文件名只是线索；配音文件必须用语音识别和人工对照文稿核实实际内容。

### 2. 确定旁白和时间轴

根据实际画面重写或拆分旁白短句。剧本标注的总时长只是参考，最终时长由实际画面、配音自然停顿和合理收尾决定。不要为了凑剧本秒数复制长时间末帧。

时间轴的基本原则：

- 保持外层集数顺序和集内 shot 顺序。
- 让点击、闪退、重新打开、分析、确认等动作与对应词句对齐。
- 先裁掉没有叙事作用的静止尾段，再适度变速；需要慢放时使用光流补帧。
- 优先调整画面有效范围，不要为了迁就画面而把整段旁白加速到不自然。
- 如果某一句明显过快，只调整对应语句，并同步顺延后续镜头和字幕。
- 结尾说完最后一句后保留自然尾音，随后结束，不自动追加解释或长空镜。

### 3. 生成和核对旁白

本地 CosyVoice 入口与 CUDA 环境安装见 [CosyVoice接入说明](docs/CosyVoice接入.md)。模型和虚拟环境独立存放，不随工程分享；生成后仍须核对实际语音内容。

补录或合成时，使用本批用户指定的参考音频和准确文稿。要匹配音色、音高范围、语速、停顿、响度和录音质感；不要只选一个“男声”就认为一致。生成完整句子后，再根据目标语速做轻微的保留音高变速。

统一处理到 48kHz、单声道中间文件，最终导出时转双声道 AAC。建议响度起点为 `loudnorm=I=-16:TP=-1.5:LRA=7`，但仍要检查句间音量跳变和尾音是否被切掉。语音识别只能辅助核对漏字、重复和同音字，不能代替实际试听或主观判断。

### 4. 制作字幕

字幕应来自最终确认的旁白文稿，按自然短句分行，跟随实际语音出现和消失。默认样式可以从本项目开始：微软雅黑、白字、深色描边和阴影，重点词使用暖黄色加粗；4K 字号约 112，底部安全边距约 155，但新画面需要重新检查。

先检查原视频是否已经烧录字幕。若用户要求恢复原画面，就保留原视频内容，只叠加新字幕；如果用户要求避免重复显示，才在明确授权后做局部裁切或清理。不能把原生画面文字和新增字幕混为一层。

同时保存可编辑的 ASS 和通用 SRT。长句要拆分，不能遮住人物、按钮、手机界面和原生关键信息。

### 5. 导出4K

默认横屏输出 `3840×2160`，优先保留素材帧率；本项目素材为24fps。720p素材可用 Lanczos 放大并轻度锐化，但放大不会恢复真实拍摄细节。推荐起点：H.264、yuv420p、AAC 48kHz/192kbps、`+faststart`。

示例滤镜：

```text
scale=3840:2160:flags=lanczos,unsharp=5:5:0.35:5:5:0
```

音频拼接后要重建连续时间戳，例如 `asetpts=N/SR/TB`，再检查最终文件的声音长度；不要只看字幕时间表判断同步。

### 6. 最终核验

运行：

```powershell
python scripts/verify_output.py output\你的最终文件.mp4
```

还要人工或抽帧检查：

1. 最终 MP4 的尺寸、帧率、时长、音视频轨和完整解码。
2. 成片是否仍然按照“集数优先、集内 shot 升序”播放。
3. 每个镜头是否来自对应的源文件，切点是否有动作，是否出现长定格、重复帧或光流重影。
4. 旁白是否完整、没有漏字、重复、切尾、突兀静音和明显音量跳变。
5. 字幕是否与旁白同步，关键词、标点、字体、边距和遮挡是否正确。
6. 最后一句说完后是否自然结束，没有未经要求的后续画面或旁白。

把输入文件哈希、实际时间轴、导出参数和核验结果写入 `output/`。旧版本的报告、截图或脚本参数不能代替对新导出文件的检查。

## 三、画面文字和错字处理规则

先区分三类文字：原视频内置文字、新增字幕、后期绘制的UI文字。用户说“只添加旁白和字幕”时，不能重绘原视频UI，不能为了修一个小字覆盖整块原画面。只有用户明确要求修复画面内文字时，才逐项记录原文、修正内容、时间点和前后截图。

如果原画面文字难以辨认，优先在旁白和字幕中使用准确文案；不要把 OCR 的不确定结果直接当成事实。重绘面板必须保留在独立版本中，不能混进“原画恢复版”。

## 四、声音、字幕和画面版本管理

每次修改都建立独立版本目录，例如：

```text
output/full_story_v1/
output/full_story_v2_original/
output/full_story_v3_slow_sentence/
```

保留原素材、旧成片和可编辑字幕，不覆盖用户已经认可的版本。每个版本的说明至少写清：输入素材批次、排序规则、旁白来源、改动句子、画面是否修改、导出规格和核验结果。

## 五、本包内容

- `docs/视频制作经验规则.md`：完整经验规则和验收标准。
- `docs/项目约定.md`：本项目约定的执行入口和沟通原则。
- `scripts/scan_assets.py`：扫描视频、音频和剧本，建立素材清单。
- `scripts/verify_output.py`：验证最终 MP4 的4K规格、音轨和完整视频解码。
- `templates/project_config.example.json`：新工程配置模板。
- `project_config.json`：当前本地工程配置；复制工程后可直接修改。
- `case_reference/pipeline_v3_original/`：当前案例“恢复原画、仅加旁白字幕、单句放慢”的参考脚本和交付说明。它依赖原案例的 `work/revision_v2/` 中间文件，供理解流程和复盘使用；新项目需要根据自己的素材重建时间轴，不能直接套用路径、时刻或句子。

## 六、环境建议

推荐 Windows + PowerShell、Python 3.10+、FFmpeg。Python 基础依赖包括：`av`、`numpy`、`Pillow`、`soundfile`、`imageio-ffmpeg`。语音识别、OCR、TTS 模型和 CUDA 环境不随本包提供，应根据项目的声音授权、机器配置和模型许可另行安装。

不要把模型权重、虚拟环境、缓存、临时帧、完整视频或音频复制进分享包。分享前检查压缩包内容，确认只留下文档、脚本、模板和小型案例说明。

## 七、案例经验结论

本项目最终形成的关键经验是：排序必须由“外层集数、内层 shot”两级数字决定；旁白必须核实实际内容并保持自然语速；语速问题要精确到具体句子；画面文字修复必须与“只加旁白字幕”分开管理；最终交付必须对真实导出的 MP4 做规格、顺序、同步、字幕和完整解码核验。
